# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 觀察：打烊剩貨全部報廢，且 16 份以上會多收 50 元清運費（規則書）。推測：備貨比實際購買的人數多，但要看盤點才確定是哪樣菜 | 看倉庫盤點 `inventory`，只減少報廢多的那樣菜（依 賣出＋沒買到 估量）；一次最多改 3 處 |
| 嫌太貴很多 | 觀察：價格超過客人剩下的預算。推測：定價偏高，但也可能是客人預算本來就低 | 先確認是哪樣菜、哪幾天；只對那樣菜小幅降價並說明犧牲單份收益，不一次全降 |
| 想吃的沒上架很多 | 觀察：客人想吃的菜今天沒賣。推測：上架組合與客人需求不合，但只能上架 4 樣 | 找出被點最多的沒上架菜，考慮換掉賣得最差的一樣；換之前先算新菜成本與總備貨份數 |
| 因為討厭的菜不進門 | 觀察：上架了某位客人討厭的菜，他直接不進門，也不留評價。推測：這樣菜擋掉了一部分客人 | 比較「擋掉的人數」與「這樣菜的收入」，再決定是否下架；一次只換一樣 |
| 星等往下掉 | 觀察：打烊時滿意比例太低或不滿比例太高（規則書星等表）。推測：缺貨造成「不滿」、價格高於建議售價造成「普通」 | 先看不滿（什麼都沒買到）是否來自缺貨或沒上架，再調備貨或上架；價格要超過建議售價時要說明風險 |
| 我自己發現的現象：宣傳後增加來客，但淨利未改善 | 觀察：來客數增加，但淨利沒有比較好。要先核對，不直接下結論。推測：新增收入不夠抵宣傳費與新增備貨成本，或增加的客人遇到缺貨變成不滿，或報廢增加 | 先算：新增收入 − 新增備貨成本 − 宣傳費 − 新增清潔費。若為負，就把宣傳費降回 0 並單獨比較；若為正但星等下降，再檢查缺貨 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
